**Achates — iOS and macOS UI review**

September 17, 2026 · Working tree based on commit `3f6af7a`

This is the original review, recorded before implementation. See [implementation status and validation](ui-implementation-2026-09-17.md) for the subsequent changes; source line references below describe the pre-change tree.

Achates has a sound native foundation. The biggest opportunity is to make the everyday conversation experience more coherent, predictable, and comfortable, then give the Mac version a fuller desktop interaction model. I would preserve the agent identity, straightforward chat layout, SF Symbols, native navigation, and mostly restrained decoration.

This review covers all 25 files in `apple/Achates/Views`, the app scenes, typography and color utilities, and the state/model code relevant to their behavior. Findings are based on source inspection, with current Apple guidance checked for platform recommendations. **No running build was visually inspected, and no accessibility or interaction tests were executed.** Dimensions, contrast, toolbar composition, focus behavior, and SwiftUI lifecycle concerns identified below need the device checks at the end. Source-confirmed behavior is distinguished from design recommendations and runtime risks. No application code was changed.

**Recommended direction**

A quiet, content-focused conversation app: clear agent identity, a comfortable transcript column, a compact composer, readable secondary information, and predictable editing. Use color for identity and meaningful actions. Keep management and diagnostic detail available without making the primary screens feel like server administration.

Keep iPhone navigation sequential and touch-friendly. Keep Mac navigation spatial, resizable, and keyboard-friendly. Share names, status meanings, typography roles, editor rules, and component behavior across platforms; adapt their density and presentation to each device.

Modernization should start with standard system navigation and controls. Apple’s current design guidance places Liquid Glass in the controls/navigation layer; standard components acquire the platform treatment automatically when built with the appropriate SDK. Preserve calm, legible content surfaces and evaluate the custom composer in that context. [Apple: Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass), [Apple: Materials](https://developer.apple.com/design/human-interface-guidelines/materials).

**What is already working**

- The Mac app has a real Settings scene, a separate resizable System window, and three-column navigation. These are useful foundations to retain.
- iOS uses native navigation stacks, forms, photo/document pickers, and contextual actions.
- Agent rows show recent message previews, activity dates, and unread status; conversation rows use the same typography roles.
- The Mac composer supports multiline text, Shift–Return, image paste, file drops, and input-method composition. Preserve that work during visual changes.
- Messages are selectable; reasoning and tool activity have progressive disclosure; destructive agent and bulk conversation operations have confirmations.
- Several accessibility details are already present: speaker attribution, action labels, unread announcements, and scaled unread indicators. The remaining work is to make those practices consistent.

**1. Give every conversation its own draft — P1 · Both · Runtime risk supported by source**

Composer text and attachments live only in local `@State`. There is no draft store keyed by agent/session, and the Mac detail view has no session-specific identity. Switching between two sessions of the same agent can reuse that composer state, making an unfinished draft appear under a different conversation. Recreating the view can instead lose it. Edit mode also replaces the existing draft, and Cancel Editing clears it.

Store text, attachments, and edit state per conversation. Restore the previous draft when canceling an edit. Do not solve this only by resetting the view with `.id(sessionID)`, which prevents carryover by discarding work. Verify switching sessions, switching agents, navigating back, and editing a prior message with an existing draft.

**2. Establish one policy for saving and leaving editors — P1 · Both · Source-confirmed gaps**

Agent editing has Save and Cancel, but Cancel dismisses immediately and the sheet has no dirty-state dismissal protection. Memory and Default Models use explicit Save yet have no equivalent protection when navigating away or switching System sections. Nested prompt/model selection edits are provisional, but the UI does not explain that they still require the parent Save. Memory’s conflict-banner Reload immediately replaces local edits.

Use Save/Cancel for a complete agent-edit transaction, with a discard decision only when leaving changed work. For memory and model defaults, consistently choose explicit Save with navigation protection or a deliberate autosave design. On Mac, support Command–S and visible unsaved status. Make destructive reload read “Discard Changes and Reload,” or preserve a copy. During saves, either freeze the edited values or track the exact saved snapshot.

**3. Distinguish loading, empty content, and failed loads — P1 · Both · Source-confirmed**

Opening a session clears its messages before fetching history, while ChatView interprets an empty message array as “Start a conversation.” There is no explicit history-loading state. Memory and Jobs suppress request errors and mark their views loaded, which can show empty-state explanations after a failed first load. Costs can show only its period control after failure. Agent configuration failures leave `isLoading` true; dismissing the error leaves a spinner. Default Models falls through to an editable form after a failed load.

Adopt consistent loading/content/empty/error states, with inline Retry and retained cached content where appropriate. Never present a failed load as successful emptiness. MemoryEditView already has a useful retryable error-state pattern to reuse.

**4. Give attachment and dictation actions visible feedback — P1 · Both · Source-confirmed**

Oversized documents are skipped with console messages. File read failures, photo decoding failures, and excess attachments can disappear silently. Dictation startup errors are also only printed. Speech startup may include downloading an on-device model, but the composer has no preparing state. These actions can look broken even when the failure is expected.

Show compact inline feedback near the composer: “This PDF exceeds 32 MB,” “You can attach up to four files,” or an actionable microphone/recognition error. Report partial success when importing several files. Show progress while preparing dictation or loading photos, preserve successful attachments, and allow dismissal without losing the draft.

**5. Make “Allowed Chats” mean what its controls imply — P1 · Both · Source-confirmed**

Every agent toggle can be off while the actual meaning is “all agents allowed.” Turning off the final selected agent therefore broadens access to everyone. A footer explains this, but the visible switch state communicates the opposite.

Use an explicit “All agents” / “Selected agents” choice and show the checklist only for Selected agents. If “No agents” is a desired capability, add it with an explicit backend representation; an empty array currently means all. Rename this screen “Agent Communication” or explain directly that it controls which other agents this agent may contact.

**6. Make keyboard submission match the visible composer state — P1 · Mac primarily · Source-confirmed**

During generation, the composer’s trailing button becomes Stop, but the Mac text view still maps Return to `send()`. Neither `send()` nor `AppState.sendMessage` rejects submission while streaming. The keyboard can therefore initiate another send when the visible UI offers only Stop, replacing streaming state and clearing the draft.

Choose the intended policy—wait, queue, or interrupt—and enforce it in one submission path for both keyboard and button actions. The smallest coherent policy is to keep drafting enabled while generation runs, with Return unable to submit until completion. Label any future queue/interrupt behavior explicitly.

**7. Finish the accessibility pass on custom controls — P1 · Both · Source-confirmed dimensions; runtime verification required**

The iOS composer buttons explicitly use 36 × 36 point frames; attachment removal uses 28 × 28. Replay audio is a caption-sized plain button without a larger frame. These deserve larger activation areas even if their glyphs stay small. The custom chat header uses fixed 15/11 point type on iOS, the reasoning picker fixes its width at 180 points, and voice status fixes its height at 28 points. Those are pressure points at large text sizes.

Use at least 44 × 44 point activation areas for primary iOS custom buttons, semantic/scaled text, and adaptive form rows at accessibility sizes. Add meaningful labels to image-viewer dismissal, avatar editing, memory-conflict dismissal, and editors. Replace empty picker/text-field labels with actual control labels; adjacent visual text is not a reliable substitute for semantic labeling. Honor Reduce Motion in the custom repeating typing animation. Verify with VoiceOver, keyboard focus, and Accessibility Inspector rather than treating source labels as proof of accessibility. [Apple: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Apple: Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons).

**8. Preserve the reader’s place — P1 · Both · Source-confirmed**

Every message-count change scrolls to the bottom, even though the view tracks `isAtBottom` and has a jump-to-bottom control. A new assistant/tool message can pull someone away from the history they are reading.

Follow new content only when already near the bottom, after the person sends a message, or when they explicitly jump down. Otherwise retain the viewport and show a compact “New messages” affordance. Reset scroll state deliberately when changing conversations. Check long responses, keyboard resizing, and activity blocks appearing/disappearing.

**9. Make the information hierarchy and vocabulary explicit — P2 · Both · Design recommendation**

The first screen is titled “Chats” but lists agents. The next screen lists conversations; actions alternate between “New Chat,” “New Conversation,” and technical “session” terminology. Chat headers show the agent name rather than the selected conversation title. This becomes confusing when one agent has many conversations, especially with three columns visible on Mac.

My preferred vocabulary is **Agents → Conversations → conversation title**, with the agent as secondary context in the detail header. If “Chats” is the preferred product term, use it consistently for actual conversations and give the agent directory another explicit label. Use “Start Voice Conversation,” “Dictate Message,” and “Read Replies Aloud” to distinguish the three audio functions.

**18. Make activity and retry behavior understandable — P2 · Both · Source-confirmed behavior / design recommendation**

“Retry” regenerates an assistant response, while the failed-send banner’s Retry resends a message that did not reach the server. “Resubmit” on an earlier user message rewinds the conversation, but its label does not explain that later content is affected. Use “Regenerate Response” versus “Retry Sending.” Explain or make recoverable the effect of resubmitting an earlier message. Always surface relevant failures, even when diagnostic activity is hidden. **19. Organize agent editing around understandable tasks — P2 · Both · Design recommendation**

Identity, model controls, Dreamtime, shared memory, voice IDs/blend syntax, tools, and deletion occupy one long form. **Cross-platform consistency contract**

| Concern | Shared behavior | iPhone presentation | Mac presentation |
|---|---|---|---|
| Navigation | Agent → conversation → messages; consistent naming and current selection | Native stack, concise contextual title | Resizable split view, useful column titles and detail context |
| Composer | Same draft persistence, sending rules, edit semantics, attachment errors | Comfortable touch targets; keyboard-safe layout | Compact controls; Return/Shift–Return; paste/drop; reliable focus |
| Editing | Same validation and saved/unsaved rules | Sheet or pushed subpage with protected dismissal | Appropriate sheet/editor window; Command–S, Escape, focus order |
| Settings | Same connection/display meanings | Compact grouped settings; separate welcome experience | Settings scene and app-menu access |
| Management | Same Memory/Jobs/Models names and state feedback | Clearly named management entry | Existing dedicated resizable window, with clearer entry/title |
| Messages | Same role attribution, dates, statuses, content formatting | Touch/context actions | Selection, hover/focus actions, Find, context menus |
| Status | Same wording, severity, recovery, and offline draft behavior | Visible in the active main screen | Visible without depending on one sidebar remaining open |
| Visual identity | Same avatar, type roles, semantic action colors | Dynamic Type and touch spacing | Desktop density, system accent and appearance behavior |

**Suggested implementation sequence**

1. **Protect work and clarify state.** Draft storage, editor dismissal/save rules, streaming submission guard, loading/error states, silent-failure feedback, accurate interval descriptions, and explicit agent-access selection.
2. **Polish the daily conversation loop.** Transcript scrolling/width, title hierarchy, search and discoverable agent editing, accessible composer controls, media viewing, color/avatar consistency, and message typography.
3. **Complete platform adaptation.** Mac menu commands/focus/window sizing; iPad adaptive navigation; iPhone setup/settings simplification; voice controls; management and Costs presentation.

Keep the shared design layer small: typography roles, semantic colors, avatar rendering, status/empty/error presentation, labeled editor rows, and action sizing. Reuse behavior while allowing platform-specific containers. There is no need for a large custom component framework or a wholesale visual rewrite.

The highest-value visual result would be a more balanced chat surface with consistent identity, clearer navigation, and quieter supporting controls. The highest-value interaction result would be an app that always preserves the user’s work and clearly explains what is happening.
